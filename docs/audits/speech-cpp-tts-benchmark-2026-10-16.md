# speech.cpp と現行 Irodori-TTS の実機比較（ボイスクローン）

実施日: 2026-10-16 / 対象: `ace_kagawa`

**すべて香川先生の同一参照音声によるzero-shotボイスクローンで比較した。既成の話者プリセットや無参照の自動音声ではない。** 追加学習・LoRAは使っていない。

## 結論

> **2026-10-16 追記:** 1〜7節は参照音声を先頭10秒に切った比較で、本番（33.04秒の全長を使用）とは条件が違う。本番と同じ全長参照での再比較は [8節](#8-再比較-本番と同じ全長の参照音声3304秒) を参照（速度は約1.74倍、本人らしさの自動指標は現行がわずかに上）。

**同じ Irodori-TTS v4.1-Small・40 steps で、生成完了が約1.50倍、初音までが約1.72倍高速になった。VRAMは約66%減った。** ただしGPU使用率と瞬間消費電力は上がる。「GPUを使わなくなる」のではなく、GPUをより高い使用率で短時間使う結果だった。

MFへ変更した speech.cpp は現行Small/40 steps比で生成完了が約5.16倍、初音までが約13.4倍高速。ただし**MFへのモデル変更とC++側への実装変更を合算した数字**であり、C++化だけの効果ではない。既存の試聴記録ではSmallの方がMFより良好だったため、まずSmall/40 stepsのまま試すことを推奨する。

本番の `.env`、サービス、Tokkio構成は変更していない。現行サービスは開始時点で停止しており、現行コードの推論経路を実験プロセスから直接呼び出した。

## 1. 通常生成の測定結果

モデル常駐・ウォームアップ後、各構成50回（同じ日本語5文 × seed 1〜10）。時刻は秒。p50は中央値、p90は90パーセンタイル。

| 構成 | 生成完了 p50 | 初音 p50 | 生成完了 p90 | RTFx ↑ | GPU使用率 平均 / 最大 | VRAM最大 GiB | 電力 平均 / 最大 W |
|---|---:|---:|---:|---:|---:|---:|---:|
| Python Small / 40（現行） | 0.892 | 0.892 | 0.939 | 8.6 | 36.2% / 60% | 6.46 | 181 / 219 |
| speech.cpp Small / 40 | 0.594 | 0.518 | 0.780 | 12.2 | 86.7% / 94% | 2.20 | 254 / 277 |
| Python Small / 16 | 0.466 | 0.466 | 0.519 | 16.3 | 38.7% / 65% | 6.46 | 192 / 205 |
| speech.cpp Small / 16 | 0.292 | 0.215 | 0.401 | 25.3 | 87.0% / 95% | 2.20 | 256 / 272 |
| Python MF / 4 | 0.250 | 0.250 | 0.300 | 30.2 | 38.2% / 64% | 6.47 | 201 / 208 |
| speech.cpp MF / 4 | 0.173 | 0.066 | 0.266 | 43.6 | 61.9% / 69% | 2.16 | 242 / 246 |

- RTFx = **モデル出力音声の合計秒数 ÷ 生成完了までの合計秒数**。大きい方が速い。後処理による無音トリムの差を抑えるため、Pythonもトリム前のモデル出力尺を使った。波形・発話速度の完全一致を意味しない。
- GPU使用率・電力は各要求の測定区間内のサンプルを集計。VRAMはパラメーターだけでなく、フレームワークの予約領域・コンテキスト・作業バッファも含む。
- 電力はGPUボード全体の値であり、マシン全体の消費電力や1要求あたりの消費電力量ではない。

## 2. 同じ出力尺に固定した確認

通常生成ではPython側のモーラベースの尺上限、BF16/F16、乱数実装、末尾打ち切りなどで生成尺が変わる。速度差が単なる短い音声の生成によるものではないことを確かめるため、5文の合成尺をそれぞれ **2.4 / 6.4 / 6.4 / 10.4 / 14.4秒** に固定し、モデル内の末尾打ち切りも双方で無効にした。通常生成と同じく各構成50回。

| 構成 | 生成完了 p50 | 初音 p50 | 生成完了 p90 | RTFx ↑ | GPU使用率 平均 / 最大 | VRAM最大 GiB | 電力 平均 / 最大 W |
|---|---:|---:|---:|---:|---:|---:|---:|
| Python Small / 40 | 0.844 | 0.844 | 0.900 | 9.4 | 37.6% / 85% | 6.99 | 187 / 221 |
| speech.cpp Small / 40 | 0.533 | 0.496 | 0.803 | 13.1 | 86.7% / 94% | 2.21 | 262 / 280 |
| Python MF / 4 | 0.202 | 0.202 | 0.257 | 37.3 | 48.2% / 76% | 7.00 | 209 / 216 |
| speech.cpp MF / 4 | 0.165 | 0.067 | 0.289 | 42.7 | 62.2% / 69% | 2.16 | 242 / 247 |

合成尺を揃えても、Small/40の完了中央値は **1.58倍**、MF/4同士では **1.22倍**高速だった。通常生成のMF同士では1.44倍、初音は3.76倍。固定尺は計算量を揃えるための確認であり、自然な発話尺や品質の評価用ではない。

これは同一モデル・ステップ数・合成尺の**実装スタック比較**であり、厳密にC++という言語だけを分離した実験ではない。PythonはBF16/CUDA・全体デコード・透かし付与、speech.cppはF16/Vulkan・窓単位デコード・透かしなし。参照音声の事前エンコード有無も異なる。

## 3. 初音が早くなる理由と品質上の注意

- 現行Pythonラッパーは、文全体のサンプリング・デコード・透かし・16 kHz後処理を終えてから音声を返す。既定の `stream=true` も、完成したPCMの分割送信である。
- speech.cppも文全体のサンプリングは先に必要だが、codecの窓単位デコードで最初のPCMを返せる。MFではこの差が大きく、今回の初音中央値は約66 msだった。LLMの文章生成待ちやアバターの遅延は含まない。
- Pythonの通常Small/40 stepsでは、平均でサンプリング約755 ms、参照準備約41 ms、尺予測約37 ms、デコード約37 ms、透かし約17 msだった。参照キャッシュだけで今回の速度差すべてが消えるわけではない。
- **同じseedでも両実装の音声は一致しない。** BF16とF16の数値差もあり、同じ声・読み・品質を保証する結果ではない。
- MFや16 stepsは品質を保つ保証がない。通常Small/40 stepsを先に試し、MF・16 stepsは速度優先の別候補として聞き比べる。

### クローンの参照音声への類似度

既存のCAMPPlus話者エンコーダー（`tts/pretrained_models/campplus_cn_common.bin`）を再利用し、同じ10秒の参照音声と生成音声の埋め込みのcosine類似度を計算した。6構成×50音声、計300音声。全音声を16 kHzにリサンプルし、CPUで同じ処理を行った。

| クローン構成 | 参照とのcosine平均 | 音声間の標準偏差 | 音声数 |
|---|---:|---:|---:|
| Python Small / 40 | 0.709 | 0.033 | 50 |
| speech.cpp Small / 40 | 0.687 | 0.032 | 50 |
| Python Small / 16 | 0.712 | 0.044 | 50 |
| speech.cpp Small / 16 | 0.686 | 0.041 | 50 |
| Python MF / 4 | 0.678 | 0.057 | 50 |
| speech.cpp MF / 4 | 0.669 | 0.044 | 50 |

今回の指標ではSmall/40のspeech.cpp側はPythonより平均0.022低く、**声の再現度が完全に同じとは言えない**。MFは双方でSmallより低かった。ただし中国語用CAMPPlus由来の自動指標であり、0.709を「70.9%本人の声」と解釈してはいけない。テキスト・尺・無音・録音条件にも依存し、日本語の知覚品質を保証する閾値や有意差判定は設けていない。Python出力のトリム等とC++未処理の差も含む。参照音声を含む聞き比べページで本人らしさを確認する必要がある。

### クローン用の前処理時間（生成時間と別計測）

| 処理 | 実測値 | 頻度・条件 |
|---|---:|---|
| Python Small/40の参照準備 | 約41 ms | 現行経路では各生成要求に含む（50回の平均） |
| speech.cpp: 参照WAVを常駐workerへ登録 | 約64 ms | GPUでエンコード、初回を除く3回。登録後は同じvoiceを再利用 |
| speech.cpp: 事前作成済みvoice GGUFを登録 | 約4.5 ms | 初回を除く3回。今回の生成比較はこちらを利用 |
| speech.cpp: voice GGUFのCPU作成 | 約5.325秒 | 8 threads、独立プロセス3回の中央値。起動・codec encoderロードを含む。一度作れば再利用可能 |

voice GGUF作成の5秒を毎回の発話に払う必要はない。反対に、毎要求でプロセス起動・モデルロード・voice作成をやり直せば、今回の常駐時の速度にはならない。登録は同じファイルを異なるvoice名で行い、初回のウォームアップを除いた。

### 読みの補助確認

seed=1の6構成×5文（30音声）を、別GPUでWhisper large-v3-turboへ文字起こしした。Small/40の中長文では元の内容を概ね回収できた一方、speech.cppの短文には入力にない「この場」、Small/16では「室田」がASR上に現れた。MFでは「材料強度学」が「材料共同学」と認識された例もある。ASR自身の誤認識・無音への幻覚の可能性があるため、これだけでTTSの誤読と断定はしないが、**短文の尺上限と実音声の確認なしに本番置換しない**。

特にSmall/40の短文のモデル出力尺中央値はPython 2.52秒に対しspeech.cpp 3.44秒だった。現行の短文の尺上限がC++へ自動で引き継がれないことも、この差に含まれる。

主観評価（MOS）、多人数同時利用、LLM/rendererとGPUを共有した場合の競合は未測定。

**VulkanとCUDAの番号順が異なる点に注意。** このホストでは `Vulkan1` が物理GPU 0、`Vulkan0` が物理GPU 1だった。予備計測で検出後、同じ物理GPUへ揃え直した。各要求で監視GPUのモデルメモリを検査している。最終集計は `final/` のみを使用し、それ以前の予備計測は除外した。

HTTP通信、FastAPIのスレッド移譲、Tokkio側のキュー・LLM・アバター・音声再生遅延は含まない。C++側はJSON/base64のworker通信を含む。Python側の通常生成は現行の尺上限・トリム・フェード・ゲインを含み、C++側に同じ後処理を実装していない。したがって「Tokkioでユーザーが体感する待ち時間がそのまま同倍率になる」とは判断しない。

## 5. Tokkioへ接続する前に必要なこと

ベースURLの置き換えだけでは互換にならない。

1. Irodori出力の48 kHz PCMを、現行契約の16 kHz mono s16leに変換する。
2. 現行の `stream` 引数、`/healthz`、`X-Sample-Rate-Hz` 等の契約を変換する。speech.cppのヘルスは `/health`。HTTP PCMでは未知の `stream` をそのまま送らない。
3. `kagawa` voiceを登録し、既存の固有名詞・数字の正規化、短文の尺上限、音声後処理、必要な固定句キャッシュを維持する。
4. **speech.cppは透かし付与・LoRA未対応。** 今回Python側の透かしは有効だった。同等機能が必要なら未対応のまま本番置換しない。
5. 通常Small/40 stepsから試聴を始め、問題がなければ16 stepsやMFを別設定として評価する。

GPUメモリの節約はLLM・rendererとの併用には有利だが、今回GPU使用率が上がったため、併用時の遅延は別途計測が必要。

## 7. 追加比較: v4-Large / 500M-v3

同日、未比較だった **v4-Large（Python BF16 / speech.cpp F16・Q8_0、各40・16 steps）** と **500M-v3（Python、40 steps）** を追加測定した。全構成で同じ香川先生の参照音声の先頭10秒を使用し、追加学習・LoRAなしのzero-shotクローン。通常生成は新規7構成×50回、固定尺は3構成×15回、Q8の再確認15回で、**新たに計410回**測定した。以下の「既報」行は前節の測定値を引用したもので、追加測定とは区別する。

### 7.1 通常生成・ボイスクローン

生成完了・初音は秒、中央値。GPUは要求区間内の平均、VRAMは最大。話者cosineは各50音声の平均であり、本人一致の確率やMOSではない。

| 構成 | 生成完了 | 初音 | GPU平均 | VRAM GiB | 電力平均 W | 話者cosine |
|---|---:|---:|---:|---:|---:|---:|
| Python Small / 40（現行・既報） | 0.892 | 0.892 | 36.2% | 6.46 | 181 | 0.709 |
| speech.cpp Small F16 / 40（既報） | 0.594 | 0.518 | 86.7% | 2.20 | 254 | 0.687 |
| speech.cpp MF F16 / 4（既報） | 0.173 | 0.066 | 61.9% | 2.16 | 242 | 0.669 |
| Python 500M-v3 / 40 | 0.837 | 0.837 | 32.8% | 5.16 | 165 | 0.710 |
| Python Large BF16 / 40 | 1.638 | 1.638 | 51.0% | 14.69 | 226 | 0.688 |
| speech.cpp Large F16 / 40 | 1.317 | 1.248 | 93.1% | 7.05 | 283 | 0.661 |
| speech.cpp Large Q8_0 / 40 | 1.709 | 1.642 | 70.8% | 4.02 | 257 | 0.660 |
| Python Large BF16 / 16 | 0.821 | 0.821 | 50.0% | 14.69 | 222 | 0.677 |
| speech.cpp Large F16 / 16 | 0.596 | 0.524 | 90.0% | 7.05 | 280 | 0.655 |
| speech.cpp Large Q8_0 / 16 | 0.737 | 0.671 | 72.3% | 4.02 | 259 | 0.655 |

**Large F16 / 40は同じLargeのPython / 40より約1.24倍高速、VRAM約52%減。** GPU使用率は51%→93%、GPU平均電力は226→283 Wとなった。Large F16 / 16同士では約1.38倍高速だった。

ただし、**Large Q8_0 / 40の通常生成はPython / 40より中央値で約4%遅かった**。F16版と比べても約30%遅い。VRAMはPythonの14.69 GiBから4.02 GiBへ約73%削減できたが、「量子化すれば生成も必ず速くなる」という結果ではない。Q8の16 stepsもF16の16 stepsより遅かった。

Q8 / 40の通常生成を別プロセスで再確認したところ、同じ5文×seed 1〜3の15回で中央値 **1.688秒**（初回の同じ15回は1.723秒）となり、遅めの傾向を再現した。**15音声すべてが初回とWAVのSHA256まで一致**しており、別の音声・尺を生成したための差ではない。

### 7.2 同じ尺への固定による確認

前節と同じ2.4 / 6.4 / 6.4 / 10.4 / 14.4秒に固定し、末尾打ち切りを無効化。5文×3 seedの15回ずつ。ウォームアップは通常生成と同じく全5文を2回ずつ行った。

## 8. 再比較: 本番と同じ全長の参照音声（33.04秒）

1〜7節は両実装とも参照音声を**先頭10秒に切って**比較した。一方、本番のIrodoriサービスは参照上限を指定せず（v4.1の既定は120秒）、`kagawa_voice_ref_48k_mono.wav` の**33.04秒をすべて**使っている（unitの環境変数と `default_max_ref_seconds=120` で確認、計測中に参照の切り詰め警告は0件）。そこで同じ日に、全長の参照で現行と speech.cpp を比べ直した。speech.cpp の voice GGUF も33.04秒の全長から作り直した。

### 8.1 結論

- **速度: speech.cpp Small/40 は現行より生成完了が約1.74倍、初音までが約1.98倍速い**（CPUが空いている状態での中央値 1.008秒 → 0.578秒、初音 1.008秒 → 0.510秒）。VRAMは6.39 → 2.21 GiB。
- **本人らしさ: 自動指標では現行がわずかに上**。CAMPPlusのcosineは現行0.721、speech.cpp 0.692（差 −0.029、95%CI [−0.044, −0.014]）。TTSに渡していない本人の別録音を基準にしても差は同程度（−0.024、[−0.039, −0.009]）。本人どうし0.76〜0.87、別人0.07〜0.11の幅に比べると小さい差で、聞き分けられるかは試聴で確認する。WavLM-SVでは差が出なかった（後述のとおり別人でも0.83と高く、この用途では区別力が低い）。
- **speech.cpp を本番相当にするには、短い文の尺上限が必須**。上限なしでは「少々お待ちください。」の後に意味のない発話が10回中9回付いた。16文字以下の文に `seconds`＝現行と同じ尺上限を渡すと0/10になった（下記の「＋尺上限」）。ただしこの規則は、16文字以下なら予測尺にかかわらず尺を固定する。現行は予測が上限を超えたときだけ縮めるので、予測が上限より短い短文では尺が伸びる。今回の短文は1文だけで、その場合は未検証。
- **voice GGUF の作り方で声の近さが変わる**。同じ参照から GPU（Vulkan）で作った voice GGUF では音声が変わり、CAMPPlusは0.675（現行との差 −0.046、5文すべてで低い）まで下がった。CPUで作った voice（0.692）を使う。作成は約99秒だが一度だけでよい。
- **全長参照は10秒参照より本人らしいとは言えない**。クローン元の録音とのcosineは+0.02上がったが、本人の別録音とのcosineは変わらなかった（Python +0.003、C++ +0.001、どちらも95%CIが0をまたぐ）。上がった分は「その録音の収録条件に近づいた」ものと考えられる。
